TASK 01 — LOCAL EMBEDDED CONTROL

ESP32 Web Server & HTML LED Control

Hosting an embedded HTTP web server on port 80 to control physical hardware via browser GET requests.

1. Overview

The objective of Task 1 was to understand how a microcontroller can provide a web interface and use an HTTP request to control physical hardware. I used an ESP32 development board, connected it to a local Wi-Fi network, created a basic HTTP server on the board, and controlled the built-in LED connected to GPIO 2 from a web browser. No external LED or breadboard was required because the development board already contains the indicator LED on GPIO 2.

2. Concepts

GPIO 2 is configured as a digital output pin. A HIGH (+3.3V) or LOW (0V) digital state is used to control the onboard LED. The core client-server architecture operates as follows:

  • Client (Browser): Sends HTTP GET requests when buttons are pressed.
  • Server (ESP32 WebServer): Listens on port 80 and maps URL routes (`/on`, `/off`) to physical GPIO state changes.
  • Local Wi-Fi Network: Acts as the communication medium carrying network packets between client and server.

3. System Design

The sequence below illustrates how a browser button press travels through the local Wi-Fi network to change the physical LED state on GPIO 2:

Browser Client │ │ HTTP GET request (/on or /off) ▼ Local Wi-Fi Network │ ▼ ESP32 Web Server (Port 80) │ ├── GET /on ──► GPIO 2 HIGH ──► Built-in LED ON └── GET /off ──► GPIO 2 LOW ──► Built-in LED OFF

5. Wiring / Setup

No external breadboard circuit was required for Task 1. The onboard blue LED is pre-wired to GPIO 2.

ESP32 GPIO 2 ───► Onboard LED (Anode) ───► Resistor ───► GND GPIO 2 HIGH ──► LED ON GPIO 2 LOW ──► LED OFF

6. Implementation

The firmware implementation follows four core stages:

  1. Wi-Fi Initialization: Using WiFi.begin(ssid, password) to join the local access point and acquire an IP address.
  2. HTTP Server Initialization: Creating WebServer server(80) on standard port 80.
  3. Route Handling: Mapping routes server.on("/on", handleOn) and server.on("/off", handleOff) to C++ handlers that invoke digitalWrite(2, HIGH) and digitalWrite(2, LOW).
  4. Client Processing Loop: Continuously invoking server.handleClient() inside loop().

7. Configuration Procedure

  1. Configure Wi-Fi credentials in the ESP32 source code.
  2. Upload firmware using Arduino IDE and open the Serial Monitor at 115200 baud.
  3. Note the local IP address printed by the ESP32 (e.g., 192.168.1.50).
  4. Open the IP address in any web browser connected to the same Wi-Fi network to access the control page.

8. Evidence & Visual Verification

Figure 1.1: Web browser control buttons and Serial Monitor log displaying assigned local IP address and GET request handling.
Video 1.1: Muted physical demonstration of ESP32 GPIO 2 LED turning ON and OFF in response to browser HTTP requests.

9. Challenges & Fixes

Limitation: The main architectural constraint was that the ESP32 operated as a purely local web server. The browser client required direct local network IP reachability. If the browser device switched to cellular data or another router, it could not access port 80.

Resolution: This local reachability limitation provided the primary motivation for transitioning from local HTTP servers to cloud MQTT message brokers in Task 2.

10. Reflection

Task 1 gave me a practical understanding of client-server communication on an embedded device. I learned that an HTML button does not directly control a GPIO; it creates a network request, the ESP32 interprets the request, and the resulting software action changes the electrical state of the pin. I also learned how Wi-Fi connectivity, IP addressing, HTTP routes, and GPIO control fit together as one system.

TASK 02 — CLOUD MQTT MESSAGING

Adafruit IO Dashboard & MQTT

Decoupling clients and microcontrollers using publish/subscribe MQTT cloud architecture to control an AC relay on GPIO 23.

1. Overview

Task 2 extended the basic ESP32 control architecture into a cloud-connected IoT system. Instead of a browser communicating directly with the ESP32's local IP address, the ESP32 connects to Adafruit IO using the lightweight MQTT protocol. The cloud dashboard publishes command values to an Adafruit IO feed, and the ESP32 subscribes to that feed, listening for updates and controlling a 5V relay module connected to GPIO 23.

2. Concepts & MQTT Architecture

MQTT (Message Queuing Telemetry Transport) is a lightweight publish/subscribe protocol operating over TCP/IP:

ElementRole in this Project
Adafruit IO DashboardPublisher — Publishes ON/OFF commands to the relay feed
Adafruit IO MQTT BrokerBroker — Receives published messages and routes them to active subscribers
ESP32 MicrocontrollerSubscriber — Subscribes to the /feeds/relay feed on port 1883
Relay FeedMQTT Topic — Named data channel carrying commands (`1`/`0` or `ON`/`OFF`)

3. System Design

Adafruit IO Web Dashboard │ │ Publish command (1 / 0) ▼ Adafruit IO MQTT Broker (io.adafruit.com:1883) │ │ Relay Feed Topic: user/feeds/relay ▼ ESP32 MQTT Subscriber │ │ GPIO 23 (HIGH / LOW) ▼ 5V Relay Module ──► AC Load / Bulb

4. Hardware & Software Specifications

ItemRole & Specification
ESP32 BoardWi-Fi controller and MQTT subscriber
5V Relay ModuleOptocoupler isolation switching interface driven by GPIO 23
Bulb / LoadPhysical output connected across relay terminals
WiFi.hESP32 network connection library
Adafruit_MQTT.hMQTT protocol handling and feed subscription management
Adafruit IOCloud MQTT broker and dashboard host

5. Wiring / Setup

ESP32 GPIO 23 ───► Relay IN ESP32 GND ───► Relay GND ESP32 5V/VCC ───► Relay VCC Relay COM ───► AC Live In Relay NO ───► Bulb Live Terminal

6. Implementation

The code configures an Adafruit_MQTT_Client with server credentials and instantiates Adafruit_MQTT_Subscribe relayFeed. Inside loop(), the ESP32 calls mqtt.readSubscription(5000) to listen for incoming feed packets. When data arrives, it parses the payload string: if "1" or "ON", GPIO 23 is set HIGH; if "0" or "OFF", GPIO 23 is set LOW.

7. Configuration Procedure

  1. Create an account on Adafruit IO and obtain your AIO Key.
  2. Create an MQTT feed named relay.
  3. Build an Adafruit IO Dashboard with a Toggle Switch block tied to the relay feed.
  4. Flash the ESP32 with your Wi-Fi and Adafruit IO credentials and verify MQTT connection in Serial Monitor.

8. Evidence & Visual Verification

Figure 2.1: Adafruit IO dashboard showing active relay feed toggle and message feed stream.
Figure 2.2: Serial Monitor log demonstrating MQTT connection success and feed subscription payload parsing.

9. Challenges & Fixes

Challenge: Occasional MQTT socket disconnections occurred during idle periods due to router timeout rules.

Fix: Implemented automatic keep-alive pinging mqtt.ping() and an auto-reconnect function MQTT_connect() inside the main execution loop.

10. Reflection

Task 2 taught me why MQTT is useful for IoT systems. In Task 1 the browser had to know the ESP32's local address. With MQTT, the ESP32 and the dashboard communicate through a broker and a feed. I learned the roles of publisher, subscriber, broker and feed, and I saw how a cloud message can be converted into a physical relay action.

TASK 03 — VOICE & CLOUD AUTOMATION

IFTTT + Adafruit IO IoT Automation

Triggering cloud actions via Google Assistant voice commands without altering the underlying microcontroller firmware.

1. Overview

Task 3 builds directly on Task 2. The ESP32 MQTT firmware remains completely unchanged because the Adafruit IO relay feed is still the final control channel. The new addition is the cloud automation layer: IFTTT (If This Then That) captures Google Assistant voice triggers and automatically publishes corresponding payload values to the Adafruit IO relay feed.

2. Concepts

Automation removes the requirement for a user to manually operate a dashboard UI. A predefined voice trigger initiates an automated web applet hook:

IF THIS (Voice Command Detected) │ "Okay Google, activate bulb ON" ▼ THEN THAT (IFTTT Action) │ Publish "1" / "ON" value to Adafruit IO relay feed ▼ MQTT Broker (Adafruit IO) │ ▼ ESP32 Subscriber (GPIO 23) ──► Relay ──► Bulb

3. System Design

Google Assistant / Voice Trigger │ │ Webhook / Event Trigger ▼ IFTTT Applet │ │ Action: Send data to Adafruit IO ▼ Adafruit IO Relay Feed (Broker) │ │ MQTT Protocol ▼ ESP32 (GPIO 23) │ ▼ Relay Module ──► Physical Bulb

4. Hardware & Software Specifications

ItemRole & Connection
ESP32 FirmwareTask 2 MQTT code (subscribes to relay feed)
Relay ModuleControlled by GPIO 23
Adafruit IOMQTT broker hosting the relay feed
IFTTT PlatformCloud bridge connecting voice triggers to Adafruit IO actions
Google AssistantVoice command trigger source

5. Wiring / Setup

Physical setup is identical to Task 2: Relay control pin connected to ESP32 GPIO 23.

6. Implementation & Applet Rules

Two IFTTT applets were configured:

  • ON Applet: Trigger: "Okay Google, activate bulb ON" ──► Action: Adafruit IO Save data to relay feed with value ON.
  • OFF Applet: Trigger: "Okay Google, activate bulb OFF" ──► Action: Adafruit IO Save data to relay feed with value OFF.

Because IFTTT modifies the Adafruit IO feed directly over HTTPS API, the ESP32 receives the update seamlessly via its active MQTT subscription without any code changes.

7. Configuration Procedure

  1. Connect IFTTT account to Google Assistant and Adafruit IO services.
  2. Create the ON voice trigger applet and set the Adafruit IO action feed to relay.
  3. Create the OFF voice trigger applet.
  4. Speak the voice command into a smartphone/smart speaker and observe the feed change in Adafruit IO and the relay toggle on GPIO 23.

8. Evidence & Visual Verification

Figure 3.1: Configured IFTTT applets showing Google Assistant triggers mapped to Adafruit IO relay feed action hooks.
Video 3.1: Muted physical relay response demonstration triggering automatically upon cloud feed updates.

9. Challenges & Fixes

Architectural Insight: I learned that adding voice automation does not require altering embedded C++ firmware. By keeping the cloud broker as a decoupled abstraction layer, third-party automation platforms (IFTTT, Zapier, Google Home) can control hardware independently.

10. Reflection

Task 3 showed me how an IoT system can be extended without rewriting the embedded control logic. The same MQTT subscriber used in Task 2 could accept commands generated by an automation platform. I learned to separate the trigger layer from the device-control layer: IFTTT handles the trigger and action, Adafruit IO handles the feed/broker side, and the ESP32 remains responsible for the physical output.

TASK 04 — FIREBASE CLOUD DASHBOARD

Firebase IoT Monitoring Dashboard

Live environmental telemetry monitoring (DHT11 & LDR) and authenticated cloud control using Firebase Realtime Database.

🌐 Hosted Production Web Application

Task 4 and Task 5 are deployed and live on Firebase Hosting:

LIVE APPLICATION: https://smartlightingiot.web.app/ ↗

1. Overview

Task 4 moves the project from a simple cloud relay control system to a complete environmental monitoring dashboard. The ESP32 reads ambient temperature and humidity from a DHT11 sensor and light intensity from an LDR sensor, transmits live readings to Firebase Realtime Database, reads user control settings from Firebase, and drives an active-low relay connected to GPIO 26. A web dashboard authenticates users and displays live values while allowing manual ON/OFF, AUTO/MANUAL mode, and LDR threshold settings.

2. Cloud Architecture Concepts

ConceptDefinition & Project Role
BaaS (Backend as a Service)Firebase provides managed database, authentication, and hosting backend functions.
Firebase Realtime DatabaseJSON cloud database enabling instant data synchronization between ESP32 and web app.
Authentication & AuthorizationFirebase Auth verifies user identity via email/password before permitting database access.
Active-Low Relay LogicDigital output pin state inversion: LOW turns relay ON; HIGH turns relay OFF.

3. System Design

5. Wiring / Setup

DHT11 VCC ──► 3.3V | DHT11 DATA ──► GPIO 4 | DHT11 GND ──► GND LDR VCC ──► 3.3V | LDR AO ──► GPIO 34 | LDR GND ──► GND Relay VCC ──► 5V/VCC | Relay IN ──► GPIO 26 | Relay GND ──► GND

6. Implementation Highlights

The ESP32 uses WiFiClientSecure and FirebaseClient with UserAuth. The sensor loop runs every 3000ms using non-blocking millis() timing. In AUTOMATIC mode, the ESP32 compares ldrValue against ldrThreshold (default 2000): if ldrValue > ldrThreshold, it sets bulbState = true (dark environment, light ON); otherwise false. In MANUAL mode, it respects the user's manual dashboard toggle.

9. Challenges & Fixes

Issue: The relay module operated on Active-Low logic, causing the bulb to turn ON when GPIO 26 was set to LOW, which initially caused inverted UI state matching.

Fix: Implemented inverted pin driving logic in code: digitalWrite(RELAY_PIN, bulbState ? LOW : HIGH);.

10. Reflection

Task 4 changed the way I understood an IoT system. Instead of a browser communicating directly with an ESP32, the cloud database became the shared communication layer. The ESP32 publishes current sensor state and reads control values, while the dashboard reads the same backend and writes commands. I also learned the difference between authentication and authorization, and how sensor acquisition, cloud storage, web presentation and actuator control can be separated into different layers.

TASK 05 — HISTORICAL LOGGING & ANALYTICS

Firebase Logging, Automation & Data Export

Timestamped NTP historical database logging, interactive Chart.js sensor visualization, and client-side CSV data export.

🌐 Production Application & Analytics

Access the live historical logging dashboard and CSV export interface:

LIVE DASHBOARD: https://smartlightingiot.web.app/ ↗

1. Overview

Task 5 completes the Smart Lighting system by adding historical data logging, automatic lighting based on the LDR, manual/automatic operating modes, data visualization, and CSV export. The final system does not only show the current state; it records timestamped sensor and actuator states under the /history database branch so that environmental data can be inspected, graphed, and exported for spreadsheet analysis.

2. Key Engineering Concepts

  • Historical Logging: Pushing unique timestamped JSON records using Firebase push() rather than continuously overwriting a single /current node.
  • NTP Network Time Protocol: ESP32 synchronizes with pool.ntp.org via configTime() to attach accurate ISO timestamps (YYYY-MM-DD HH:MM:SS) to every log record.
  • Data Visualization & CSV Export: Integrating Chart.js for real-time sensor plotting and generating downloadable Blob CSV files directly in the browser.

3. System Design

DHT11 + LDR Sensors │ ▼ ESP32 │ ├── Every 3s ──► Update /current node in Firebase ├── Every 10s ──► Push timestamped record to /history node │ ▼ Firebase Realtime Database (/history/reading_id) │ ▼ Hosted Web Dashboard ├── Historical Log Data Table ├── Interactive Chart.js Sensor Trends Graph └── Downloadable CSV Export (.csv)

9. Challenges, Fixes & System Limitations

LDR Calibration: Analog light threshold values (e.g., 2000) depend on ambient room lighting and resistor values. Configurable cloud threshold controls solved this by allowing live recalibration.

Database Retention: Continuous 10-second logging generates substantial database records over time. For production deployments, automated Firebase Cloud Functions cleanup rules would be implemented.

10. Reflection

Task 5 brought the earlier assignments together into a complete IoT architecture. I learned that an IoT project is not only about making a sensor reading appear on a screen. The system has to acquire data, make control decisions, communicate with the cloud, preserve historical state, present information clearly, and provide a usable control interface. The addition of automatic mode also made the system behave as a closed feedback loop.
